What the server checks

Each sign-in attempt runs through these steps in order.

  1. 1Receive the credentialsEmail and password arrive over an encrypted connection.
  2. 2Find the accountLook up the email in the user table.
  3. 3Check the passwordHash the password with the account's salt and compare it with the stored hash. The real password is never stored.
  4. 4Issue a signed tokenCreate a token naming the user, then sign it with a secret only the server knows.
  5. 5Start the sessionThe browser keeps the token and sends it with every later request.

What to notice

        
    
          
  • The error message is vague on purpose. A wrong email and a wrong password both show "Invalid login credentials". The precise reason appears only in the server log, so an attacker cannot learn which emails exist.
    • 
          
  • Attempts are limited. Three wrong tries lock the form for 20 seconds, which slows down password guessing.
    • 
          
  • The token carries identity, not permissions. It contains a user ID and an expiry time. Decide what the user may do on the authorization page.
    • 
          
  • The signature stops tampering. Change one character of the token and the server rejects it, because the signature no longer matches.
    • 
        

        

          How this maps to our real system
          
In the Vacant Room Checker, Supabase Auth runs these steps on its own servers. The browser calls supabase.auth.signInWithPassword() and gets back a session containing a signed token (JWT). This page imitates that flow in the browser so you can see it, which a real system must never do: the user list, salts, and signing secret would stay on the server.
