What we connected

The Vacant Room Checker decides whether a room is vacant or occupied from RFID card taps. Those taps have to be stored somewhere that both the hardware and the web app can reach, from any network.

We chose Supabase, a hosted PostgreSQL database that also gives us a REST API, user sign-in, and live updates without writing a server. Our first proposal used PHP and MySQL on XAMPP, which only works on one computer. Supabase let a microcontroller in a classroom and a browser anywhere share the same data.

Two different clients talk to the same project:

ClientHow it connectsWhat it does
ESP32 with RC522 reader (C++)HTTPS calls to the REST APISaves each card tap, reads the room status, sends a heartbeat
React web app (Vite, TypeScript)The @supabase/supabase-js libraryShows live rooms, signs users in, books rooms, shows analytics

How the parts fit

Everything goes through the Supabase project. The hardware never talks to the web app directly, so either side can be offline without breaking the other.

Step 1: Create the project

  1. Sign in at supabase.com and create an organization. We named ours VRC_System and used the Free plan.
  2. Choose New project and name it Vacant-Room-Checker.
  3. Set a database password and save it in a password manager, because the dashboard will not show it again. Pick the region closest to you.
  4. Wait a minute or two for the project to finish provisioning. The dashboard opens when it is ready.
Before a demo

Free-plan projects can be paused after a stretch of inactivity. Open the dashboard the day before you present, and restore the project if it shows as paused.

Step 3: Copy the keys

Every client needs two values: where the project lives, and a key that proves the request belongs to it. In the dashboard, open Project Settings, then API Keys. The Connect button at the top of the dashboard shows the same values.

ValueLooks likeWhere it may be used
Project URLhttps://YOUR-PROJECT-REF.supabase.coFirmware and web app
Publishable keysb_publishable_...Firmware and web app. It is designed to be public, but only safe when Row Level Security is on (Step 4).
Secret keysb_secret_...Never. It bypasses every security rule. Keep it off the ESP32, out of the React app, and out of GitHub.
Use placeholders in anything you publish

This guide writes YOUR-PROJECT-REF and sb_publishable_... instead of our real values. Do the same in your own repository.

Step 4: Lock the tables down

Because the publishable key sits inside the firmware and the web page, anyone can find it. The database must therefore decide what that key is allowed to do. Two layers work together:

  • Row Level Security (RLS) uses policies to decide which rows a role may touch.
  • Grants decide whether a role may touch the table at all. Without a grant, a policy is never reached.

Requests that use only the publishable key run as the anon role. Signed-in users run as authenticated. Our rules:

What went wrong for us

Our rfid_logs table started with a policy named "Allow anonymous reads". It let anyone holding the publishable key list every card number ever tapped. Check yours with the query below and drop any policy you did not mean to create.

Step 5: Connect the ESP32

The ESP32 does not need a Supabase library. Supabase turns every table into a REST endpoint, so the firmware only has to send an HTTPS request with the right headers.

HeaderValueWhy
apikeythe publishable keyIdentifies the project
AuthorizationBearer plus the same keyMakes the request run as the anon role
Content-Typeapplication/jsonThe body is JSON
Preferreturn=minimalDo not send the new row back, since anon is not allowed to read rfid_logs

This is the heart of our firmware. It builds the request, posts the tap, and treats HTTP status 201 Created as success.

If Wi-Fi drops

A second ESP32 stores taps in its own flash memory and hands them back over a serial cable when the main board is online again. Each tap carries a unique ID and its original time, so a late upload never counts twice and never loses its real timestamp. This is why rfid_logs has a client_tap_id column with a unique index.

Step 7: Turn on real-time

Realtime streams table changes to the browser over a WebSocket. It is off for each table until you add the table to the supabase_realtime publication.

In React we subscribe to changes on rooms and update the screen when one arrives:

Why we listen to rooms, not rfid_logs

Public visitors may see room status but not card numbers. The tap history stays private, and a trigger (next step) copies just the status into rooms, which everyone may watch.

Step 8: Automate with triggers

The ESP32 only inserts a row. A database trigger does the rest, so the logic lives in one place and cannot drift between the hardware and the web app.

Step 9: Test the connection

Test from the hardware outward. Each check proves one link in the chain.

  1. ESP32 to database. Tap a card. The Serial Monitor prints HTTP 201.
  2. Row stored. In Table Editor, open rfid_logs. A new row appears with your card number and the time.
  3. Trigger worked. Run the query below. The room's status matches the tap.
  4. Web app to database. Open http://localhost:5173. The CS-101 card appears.
  5. Realtime. Keep the browser visible and tap again. The card flips between Vacant and Occupied with no refresh, and the dot beside "Live" stays green.

Errors we hit

These are the real problems we ran into while connecting the system, and what fixed each one.

What we sawCauseFix
ESP32 prints Status fetch failed: 401 or Heartbeat: 401 while taps still work Tables created with SQL had no grants for the anon role, so Postgres answered "permission denied" Run the grant statements from Step 4
The dashboard shows "Loading rooms" and "Reconnecting", and the browser console lists WebSocket failures The .env file still held placeholder text (<your sb_publishable key>) instead of the real key Paste the real key with no brackets or quotes, restart npm run dev, hard-refresh with Ctrl + Shift + R
Room list is empty but "Live" is green The table has no rows, or the public read policy or grant is missing Insert the room, then check the rooms public read policy and the select grant
22P02 invalid input syntax for type uuid in the SQL Editor A placeholder or an email address was typed where a UUID belongs Look the id up from auth.users by email instead of typing it

Security checklist

Before sharing the project or uploading it to GitHub, confirm each item:

  • Row Level Security is on for every table in the public schema.
  • No policy lets anon read rfid_logs or profiles.
  • The secret key appears nowhere in the firmware, the React code, or the repository.
  • .env is listed in .gitignore.
  • The Wi-Fi password is not in the repository (keep it in a separate header file that is ignored).
  • Admin rights come from profiles.role in the database, never from something the browser can change.

What we learned

  • A cloud database gives separate devices one shared source of truth. The ESP32 and the browser never talk to each other.
  • The publishable key is public by design. Security comes from Row Level Security and grants, so set them up before the first real tap.
  • Putting the logic in database triggers kept the firmware simple and made the web app update itself through Realtime.
  • Most of our delays were permission and configuration errors, not code. Reading the exact HTTP status or console message pointed to the fix every time.
