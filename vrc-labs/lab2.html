Lab 2: Authentication vs Authorization

Every secure system asks two questions, always in the same order. Who are you? Then, what are you allowed to do?

The two ideas

Authentication (AuthN)

Who are you?

Verifying that a person or device really is who it claims to be, using evidence only they should have.

  • Email and password
  • One-time code sent to a phone
  • Fingerprint or face scan
  • RFID card tapped at a door

Authorization (AuthZ)

What are you allowed to do?

Deciding which resources and actions an already-identified person may use, based on rules the system owner sets.

  • Roles such as user and admin
  • Permissions on each table or page
  • Access policies and ownership rules
  • Time limits and suspensions

Think of an airport. The passport check proves who you are: that is authentication. Your boarding pass decides which gate you may enter and which seat is yours: that is authorization. A valid passport does not let you walk into the cockpit.

How they work together

One booking request in our system passes through both checks:

  1. The student signs in AuthNThe server checks the email and password, then returns a signed token that names the student.
  2. The browser sends the token with each request AuthNThe server verifies the signature and expiry, so it knows who is asking.
  3. The database checks permissions AuthZA policy asks: is this user allowed to create this booking, and is the account suspended?
  4. The request is allowed or refused AuthZAllowed requests succeed. Others return 403, or 401 if the token was missing or invalid.

Mistakes to avoid

  • Treating a sign-in as permission for everything. Being authenticated only proves identity. Every action still needs its own authorization check.
  • Checking roles only in the browser. Hiding the Admin link is a convenience, not security. The rule must also live on the server or in the database.
  • Letting users edit their own role. In our database a trigger resets role and strike_count on any update that does not come from an admin.
  • Revealing too much when sign-in fails. "Wrong password" confirms the email exists. "Invalid login credentials" does not.
